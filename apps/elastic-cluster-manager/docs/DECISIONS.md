# Decisions

## Made (ADR-style, revisable)
1. **Provider:** `bpg/proxmox`, exact-version pinned, subject to Milestone 0.
2. **Queue:** Procrastinate on Postgres, no Redis.
3. **TF state:** `pg` backend, one schema per cluster, plus encrypted snapshots.
4. **Clean-room** Terraform module and Ansible roles. The legacy `tf/modules/proxmox_vm` and `ansible/roles/elasticsearch` are not reused.
5. **Ansible** via `ansible-runner`, with a generated ephemeral inventory.
6. **ES versions** come from `artifacts-api.elastic.co/v1/versions` with a cache. Nothing hardcoded.
7. **Cluster identity** is `cluster_uuid`. VM correlation needs verified evidence.

## Answered by the user (2026-10-30)
1. **Terraform** (not OpenTofu), behind a runner interface.
2. **Proxmox:** a dedicated token is approved. Disposable VMs use **VMID 5xx**. Host is any pve node. The token itself is still to be provided (not by committing it).
3. **SSH to Proxmox nodes:** approved, with a dedicated key.
4. **Template:** selected by **VMID, default 8000**, as a setting (`ECM_DEFAULT_TEMPLATE_VMID`). `ECM_DEFAULT_TEMPLATE_NAME=ubuntu-25.04` is the fallback. Open question for the spike: confirm 8000 is a template on which node.
5. **Network:** VLAN 10, `192.168.10.0/24`. A DHCP-excluded static range is still to be chosen by the user. UniFi version is still unknown.
6. **Hosting:** Caddy on `infra.lab.thewortmans.org`. The app is `ecm.lab.thewortmans.org`.
7. **The existing cluster (es01–es06) is live.** Read-only discovery and adoption target only.
8. **Admin credential:** an Argon2id hash in the `ECM_ADMIN_PASSWORD_HASH` environment variable. This is more secure than a plaintext password variable, and a first-run page would be an open window before setup.
9. **Secrets policy (hard rule):** secrets are never committed. Real env files are gitignored. Only `*.example` or `*.template` copies with placeholders are committed.

## Phase 3 implementation notes
- **Deviation from ARCHITECTURE.md §10:** the VM link lives directly on `es_nodes` (`vm_id`, `link_confidence`, `link_evidence`) instead of a separate `vm_links` table. Simpler, and a node has at most one VM.
- **Proxmox connection:** one row per API endpoint. If pve1–3 form one PVE cluster, a single connection lists all three nodes. If they are standalone, add three connections. To be confirmed on the live system.
- **Correlation** uses the node's published IP against guest-agent IPs and static cloud-init IPs. Guest-agent evidence outranks configuration. MAC addresses are stored but ES does not report them, so they are not used.
- **Stale rows:** VMs, nodes and storage that disappear from a source are deleted from the observed-state tables on the next successful sync.
- **TLS:** verification is on by default. A pasted CA certificate or an explicit "skip verification" opt-in is available, and the opt-in is audited.
- **Fixtures are synthetic** (RFC 5737 addresses, invented names). They follow the real API response shapes but have not been checked against a live Proxmox or Elasticsearch yet.

## Phase 4 implementation notes (in progress)
- **Done, pure and tested:** `backend/app/desired/` holds the desired-state models, validation, topology presets and the two config rules. No database, API or Proxmox access yet.
- **Roles:** `default` omits `node.roles`, `coordinating` renders `[]`, `custom` renders an explicit sorted list. Custom needs a non-empty list of valid roles, and `voting_only` needs `master`.
- **Bootstrap:** `cluster.initial_master_nodes` is rendered only for the `create` operation while `bootstrapped_at` is unset, and lists only electable master nodes (not `voting_only`). A single-node cluster uses `discovery.type: single-node` and never `initial_master_nodes`.
- **Cluster rules (errors):** at least one electable master and one data node; a multi-node cluster needs at least 3 master-eligible nodes; unique node names and addresses; a node that holds data needs `data_disk_gb`; heap is at most half of RAM and at most 31 GB. Settings that ECM renders itself (`node.roles`, `cluster.name`, discovery and path settings, and similar) cannot be overridden through `extra_settings`.
- **Warnings (advisory):** an even master-eligible count, master-eligible nodes pinned to the same Proxmox host, and the single-node yellow-health note.
- **Presets:** `single_node`, `three_node` (all default roles) and `dedicated_masters` (3 master-only nodes plus N data and ingest nodes, optional coordinating nodes). Defaults are overridable and still validated.
- **Version catalog (done, tested):** `desired/versions.py` reads `artifacts-api.elastic.co/v1/versions`, keeps plain `X.Y.Z` releases only (the API mixes in `-SNAPSHOT` builds and aliases), caches for an hour and serves the stale copy if a refresh fails. Upgrade rules: no downgrades, target must be published, no skipped majors, and a major upgrade needs the latest published minor of the current major. The current version need not be on the published list.
- **Placement (done, tested):** `desired/placement.py` recommends a Proxmox host per node and never decides for the user. Hard filters: host online, datastore present, free RAM after a reserve (the larger of actual use and RAM configured on running VMs), vCPU room within a 2x overcommit, and free disk with a shared datastore counted once. Master-eligible nodes spread across hosts first, then headroom breaks ties. A host that would hold enough masters to break quorum if lost produces a warning, not a refusal. Deterministic, and independent of host order.
- **Network profiles and IP allocation (done, tested):** `desired/network.py` holds a validated `NetworkProfile` (bridge, VLAN, subnet, gateway, DNS, search domain, allocation range) and `allocate_addresses`. The range must be one the DHCP server never serves; ECM cannot check that, so the operator owns it. Validation rejects a gateway or range outside the subnet, a range that includes the gateway or a DNS server in the subnet, a reversed range and subnets smaller than a /29. Allocation is deterministic: nodes with a fixed `ip` keep it, the rest get the lowest free pool address, and the caller supplies every address already in use. An exhausted pool names how many addresses are missing. IPv4 only. **Stored and editable:** profiles live in the `network_profiles` table (migration `0003`) and are edited from the Infrastructure page ("Network for new nodes"), through `GET/POST /api/network-profiles` and `PUT /api/network-profiles/{id}`. A `default` profile is seeded at startup only when no profile exists, and never overwrites an edit: `192.168.10.0/24`, gateway and DNS `192.168.10.1`, VLAN 10, bridge `vmbr0`, search domain `lab.thewortmans.org`, allocation range `192.168.10.110`-`192.168.10.149`, DHCP range `192.168.10.150`-`192.168.10.254`. The first range requested, `.110`-`.150`, overlapped DHCP by one address, so it was cut to `.149`. The gateway and domain are inferred from the lab hosts' names and the spike VM answering on this subnet. The DHCP range is optional; when set, the allocation range must not overlap it, and a node with a fixed address inside it is refused. Changes are validated server-side, rejected with a plain message when inconsistent, and audited with the old and new range. The response lists addresses already used by Proxmox VMs or Elasticsearch nodes inside the range; the UI shows them as a warning, and allocation skips them anyway. Tests use RFC 5737 addresses.
- **Terraform rendering (done, tested, verified live read-only):** `backend/app/provisioning/` renders a CREATE workspace from a desired state, the placement, the allocated addresses and VMIDs, a network profile and a template reference. Static HCL (a root module plus a `modules/es_node` child module) lives in `hcl.py` and never contains user data; everything cluster-specific is serialised to `cluster.auto.tfvars.json` with sorted keys, so output is byte-identical for the same inputs, and `config_digest` fingerprints it to tie a stored plan to its configuration. Inputs are validated before rendering (hex cluster id for the Postgres schema name, Proxmox names, bridge, https endpoint, unique VMIDs of 100 or more, addresses inside the profile network). The provider is pinned exactly (`bpg/proxmox` 0.119.0); the guest agent is off by default; tags are sorted; the token is only ever named as the `PROXMOX_VE_API_TOKEN` environment variable the runner will supply. `allocate_vmids` hands out the lowest free IDs in a configurable range. **Verified:** a rendered 3-node workspace passes `terraform fmt`, `init` and `validate`, and a read-only `plan` against pve2 with the pool-scoped token reports 3 to add, 0 to change, 0 to destroy. Running it found one real bug the unit tests could not: a child module must declare its provider source, otherwise Terraform looks for `hashicorp/proxmox`.
- **Terraform runner (done, tested against the real CLI; not yet wired to operations):** `provisioning/runner.py` defines the `TerraformRunner` interface and a `CliTerraformRunner`. It runs Terraform with a minimal environment (never ECM's own, so the master key cannot leak into a provisioner; only the credentials passed in are added), redacts every output line and registers the credentials for redaction, applies only a saved plan file, and never destroys on failure: a failed apply keeps the partial state and reports which resources exist. A run past its time limit is sent SIGINT first so Terraform can release its lock and flush state, and killed only if it ignores that. `plan.py` reads `terraform show -json` and enforces what each operation may do: create only creates, update never deletes or replaces, destroy only deletes, and an adoption import must show no change at all. `workspace.py` writes rendered files under `<root>/<cluster_id>/tf` without touching state or the provider cache, and binds a stored plan to the configuration digest and the plan file hash, so an edited config or tampered plan is refused as stale. Tests use throwaway `terraform_data` configurations, so they need no provider or network.
- **Operation wiring (done, tested with a fake `TerraformRunner`; never run against real Terraform or Proxmox):** `provisioning/operation.py` drives `tf.create`, and a cleanup `tf.destroy`, through the phases `render, init, plan, approval, apply` as one job, `tf.run`. The job has no automatic retry; only a person retries.
  - **Approval gate.** `plan` stores one digest over the operation kind, the rendered configuration and the plan file (`StoredPlan.approval_digest`). The operation then pauses in `pending_approval` and the job ends, so no worker waits for a person. `POST /api/operations/{id}/approve` takes the digest the user was shown. It is refused for a dry run, for any state but `pending_approval`, and for any other digest, and it claims the operation with one conditional `UPDATE` so two clicks cannot both win. `apply` then opens the workspace as it is on disk (never re-rendering), checks it against the stored plan, checks the stored plan against the approved digest, and applies only that plan file. Regenerating a plan or editing the configuration changes the digest, so the earlier approval no longer matches. A plan that fails the safety rules for its kind (a create that deletes, updates or replaces anything) is never offered for approval. A plan with no changes needs no approval, and a missing plan record never counts as "no changes".
  - **Dry run (gate only).** `start_create(dry_run=True)` runs `render, init, plan` and stops, with no approval or apply step. The approve call refuses it, and the apply step refuses it again. The wizard control for it is still to do.
  - **Retry.** An approval never survives a retry. Failures before the plan resume where they stopped. A failure at or after the plan restarts from the plan, because after a partial apply the saved plan is stale. The new plan has a new digest and needs a new approval. `operations.result` (resources in state, non-sensitive outputs, error) is kept across retries.
  - **Cleanup.** A failed apply keeps its partial state and destroys nothing. Cleanup is a separate `tf.destroy` that a person starts by typing the cluster name. It needs a failed `tf.create` on a managed cluster that left resources in state, runs its own destroy plan, needs its own approval, and its plan is rejected if it would delete any resource the failed create did not leave in state. It can only remove what is in that cluster's Terraform state. A VM that Proxmox created but Terraform never recorded is not found by it.
  - **Other rules.** Only `managed` clusters are provisioned or cleaned up; `discovered` and `adopted` are refused. Cancel is allowed only while waiting for approval, and a late job cannot revive a cancelled operation. Terraform's environment is exactly `PROXMOX_VE_API_TOKEN` and `PG_CONN_STR` (from `ECM_TF_STATE_URL`). Migration `0004` adds the approval, plan, dry-run, parent and result columns to `operations`; it was run up, down and up on SQLite and checked against the models, and the upgrade was applied on Postgres on infra.
  - **Read-only before approval means Proxmox and Elasticsearch.** `terraform init` with the `pg` backend creates the cluster's empty state schema in the state database before any approval. That is ECM's own bookkeeping, not an infrastructure change, but it is a write. To be confirmed.
- **Worker image (built and run on infra, linux/amd64, 2026-11-05):** `backend/Dockerfile` is now staged: `base` (the app), `tools`, `worker` (base plus Terraform and the provider) and `app` (base alone, last, so a plain build is unchanged). Compose builds `worker` from the `worker` stage and `api` and `migrate` from `app`, so only the worker has Terraform and only the worker gets `ECM_TF_STATE_URL`.
  - **Verified on infra:** the worker image built, so the pinned downloads passed their checksum checks. `terraform version` in the running worker reports v1.17.0 on linux_amd64, and the provider zip is at `/opt/ecm/terraform-providers/registry.terraform.io/bpg/proxmox/terraform-provider-proxmox_0.119.0_linux_amd64.zip`. Also on infra: migration `0004` applied on Postgres (`migrate` exited 0; the new `operations` columns and the `fk_operations_parent_op` foreign key are present; only the upgrade ran there), and the worker runs as `ecm` and can write to `/data/clusters`. **Not yet verified:** the arm64 build and a `terraform init` run inside the container.
  - **Pinned and verified.** Terraform 1.17.0 and `bpg/proxmox` 0.119.0, for amd64 and arm64, each against a SHA-256 pinned in the Dockerfile. Checksum provenance, checked 2026-11-05: Terraform from HashiCorp's `SHA256SUMS`, whose signature verified against key `C874011F0AB405110D02105534365D9472D7468F` (fetched from hashicorp.com; confirm the fingerprint at hashicorp.com/security); the provider from the Terraform Registry and the GitHub release, which agree. The Terraform binary has only that one signed source. To upgrade, change a version and both of its checksums together.
  - **`docker/fetch_tool.py`** downloads over HTTPS only, hashes while writing, and renames into place only on a match, so a mismatch leaves nothing and fails the build. It retries 5xx, 429 and network errors with a growing delay (the spike saw GitHub 504s), never a checksum mismatch or a 4xx, and refuses bodies over 200 MB.
  - **Integrity is a build-time guarantee only.** Terraform does not check signatures for a `-plugin-dir` provider (it reports it as "unauthenticated"), and the lock file's hash is computed locally from whatever is in the directory. Nothing is downloaded at run time, and the directory is root-owned inside the image.
  - **Layout.** The provider zip goes in `registry.terraform.io/bpg/proxmox/` as `terraform-provider-proxmox_<version>_linux_<arch>.zip`. A test reads that path out of the Dockerfile and runs the real `terraform init -plugin-dir` against a rendered workspace (with a stand-in zip). `tests/test_worker_image.py` also asserts the Dockerfile's provider version equals `hcl.PROVIDER_VERSION`.
  - **Workspaces** live on a new `clusters` volume at `/data/clusters`, owned by the `ecm` user. The existing `appdata` volume on deployed hosts was created root-owned, so reusing it would not have been writable.
  - **State database.** By default Terraform state lives in ECM's own database (`ecm`, one `tf_<id>` schema per cluster), with the `ecm` role's credentials, not the separate `tfstate` database in ARCHITECTURE section 4. Creating a database needs Postgres DDL that could not be tested here. The connection string is built by the app from `ECM_DATABASE_URL` (`app/dburl.py`), with every part percent-encoded, and is handed to Terraform as `PG_CONN_STR`. Compose no longer builds it (see the first live run below). `ECM_TF_STATE_URL` overrides it to use another database; an explicit URL must have `# / ? @ : %` in its password percent-encoded. A dedicated, limited role is the better end state.
- **Create endpoint (done, tested with a fake Terraform; not yet run against the live Proxmox):** `POST /api/clusters` (`api/provisioning.py`, logic in `provisioning/create.py`) plans a new managed cluster and enqueues `tf.run`. Body: `name`, `version`, `preset` (with `data_nodes`, `coordinating_nodes`, or `nodes` for `custom`), optional `node_overrides` (cores, RAM, disks, heap, a host pin, a fixed IP), `proxmox_connection_id`, `network_profile`, `template_vmid`, `datastore`, `pool_id`, and `dry_run`.
  - **Dry run is the default.** A real create needs `dry_run: false`, which produces a plan that can be approved. Sending the same name again reuses the planned cluster while nothing was applied (earlier dry runs, cancelled creates, and failed creates with no result); once a create has applied anything, or while one is in progress, the name is refused with a pointer to retry or cleanup.
  - **Version** is checked against the artifacts catalog before anything else, outside the allocation lock. An unpublished version is a 422; an unreachable catalog is a 503 and the request is refused, never assumed fine.
  - **Placement** uses the existing scoring over the last discovery sync, plus the Milestone 0 rule: a node placed on a host other than the template's needs the template's disks on shared storage that host can read, otherwise the request is refused and suggests `pve_node`. No known hosts means "sync first". A sync older than 30 minutes, or a failed one, is a warning.
  - **Names:** the cluster name and every node name must be unused by any VM, Elasticsearch node or cluster, so a new node cannot be mistaken for the live cluster's.
  - **Addresses and VMIDs** skip everything in use on Proxmox or Elasticsearch, and everything promised to another real create: active ones, failed ones with partial resources until a cleanup succeeds, and succeeded ones for an hour (`RESERVATION_GRACE`) so discovery can catch up. Dry runs reserve nothing. VMIDs come from `ECM_VMID_RANGE_START`/`END` (default 500 to 599; compose does not pass these two through yet, so the default applies on infra). On Postgres the allocate-and-commit step runs under `pg_advisory_xact_lock`, so two requests cannot be handed the same address; that lock has only been tested as a no-op on SQLite.
  - **Defaults** for the template come from `template_vmid`, then `ECM_DEFAULT_TEMPLATE_VMID`, then `ECM_DEFAULT_TEMPLATE_NAME`; the datastore from `ECM_DEFAULT_STORAGE`; the profile is the one named `default`. If there is exactly one Proxmox connection it is used without being named.
- **First live dry run on infra (2026-11-05):** `POST /api/clusters` planned a three-node cluster against the live discovery data (hosts, addresses `.110` to `.112`, VMIDs 500 to 502) and the worker ran `render`. `init` then failed: compose had built the state URL by pasting the Postgres password into a string, and a `#` in the password made Terraform cut the URL short (`invalid port ... after host`). Fixed by building the URL from parts. The error had echoed the start of the password into the operation log, because the redactor only masks exact registered values. The runner now also masks the password inside any URL it is given, including the pieces a URL parser stops at (`#`, `/`, `?`). A password that appeared in a log before this fix should be treated as exposed to ECM administrators and rotated if it is reused elsewhere. The same run reported `the last Proxmox sync failed (list nodes: HTTP 401)`, so placement used stale data; that is open and must be fixed before a plan can succeed, since Terraform uses the same token. A direct request with the secret the operator holds returned HTTP 200 while ECM's own sync got HTTP 401, so the secret ECM had stored was wrong or stale; why is not known. `PUT /api/proxmox/{id}/credential` (below) replaces it.
- **Replacing a Proxmox token (done, tested against the fixture Proxmox):** `PUT /api/proxmox/{id}/credential` takes `token_secret` and optionally `token_id`. It tests the new token against Proxmox with a read-only request before saving anything: a 401 or 403 is a 422 and an unreachable host is a 502, and either way nothing is changed. On success it overwrites the encrypted secret, stamps `rotated_at`, updates the token id if given, and syncs at once, recording any sync error on the connection. The audit log records the token id and never the secret, and a rejected attempt is audited too. Secrets and token ids are now trimmed on both add and replace, because a pasted trailing newline is rejected by Proxmox with a 401. There is no UI for this yet.
- **Token rights (found on infra, 2026-11-05):** a Proxmox connection has one token, used for both discovery and Terraform, and the two need different rights. Discovery needs to read the whole datacenter: `Sys.Audit` (without it Proxmox lists a node and its status but omits its CPU and memory), `VM.Audit` and `Datastore.Audit`, for example the `PVEAuditor` role on `/`. Terraform needs rights on the `ecm` pool, the storage, and read access to the template. The token on infra was the pool-scoped one from the spike: ECM saw every node as online with no usage figures, and no VM outside the pool, so placement had nothing to work with and every check against existing machines (addresses, names, VMIDs) would have passed vacuously. Changes: a sync now fails with a message naming `Sys.Audit` and `PVEAuditor` when no online node reports CPU and memory (a single node without figures is tolerated), before anything is stored, so the last good data is kept; replacing a token is refused if it authenticates but cannot audit the nodes; placement reports "offline" and "unknown capacity" separately; and a create plan warns when ECM can see no VMs other than templates. **Not built:** separate credentials for discovery and for Terraform, which is the better end state (a read-only token everywhere, a pool-scoped one for Terraform). Until then one token needs both sets of rights. Whether the guest agent can be read (needed for the addresses of running VMs) depends on the Proxmox version and role, and a refusal there is silently treated as "no agent".
- **State connection TLS (found on infra, 2026-11-05):** with the token fixed and discovery healthy (nodes with CPU and RAM, 24 VMs, 16 with known addresses), the dry run reached `terraform init` and failed with `pq: SSL is not enabled on the server`. Terraform's Postgres driver (`lib/pq`) requires TLS unless the URL says otherwise, and does not understand `prefer` or `allow`, which `psycopg` (ECM's own connection) does; the Postgres in the compose stack has no TLS. The derived state URL now carries `sslmode` from `ECM_TF_STATE_SSLMODE` (default `disable`; `require`, `verify-ca` and `verify-full` are accepted), unless the database URL already chose one, with `prefer` and `allow` replaced by the setting. This is unencrypted, over the compose network, like ECM's own connection; use `require` or `verify-full` for a database that offers TLS. An explicit `ECM_TF_STATE_URL` is used exactly as written, so it needs `?sslmode=disable` itself if the server has no TLS. Tested with the real Terraform CLI against a fake server that refuses TLS: without the setting it fails exactly as on infra, with it the client skips TLS and reaches the server. The same run showed placement leaving pve1 unused with no explanation; a create plan now says why each unused host took nothing.
- **Not started:** the Ansible roles and the bootstrap-versus-join phases, the wizard UI and its dry-run control, marking `vms.tf_managed` after a create, and a custom Proxmox CA for Terraform (a connection with a pasted CA is not passed through). Terraform's `-plugin-dir` skips signature checks, so the pinned checksums remain the only integrity check.
